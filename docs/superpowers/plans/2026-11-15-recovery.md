# Polling Reliability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Recover from temporary provider failures automatically and expose honest freshness.
**Architecture:** Typed transport errors, finite coordinator recovery schedules, live options and snapshot diagnostics; preserve serialized reads/writes.
**Tech Stack:** Python 3.14, Home Assistant 2026.11, aiohttp, pytest, Ruff.
**Spec:** `docs/superpowers/specs/2026-11-15-recovery-design.md`

## Global Constraints

Offline synthetic tests only; no live renewals; persistent DeviceID and entity IDs unchanged.
No secrets or upstream payloads in diagnostics. No automatic write retries.
No release/version bump or publication.

## Review Focus

- Failed recovery login must leave a retryable session, not demand a PIN.
- Retry-After must survive manual refreshes, option changes and renewal preflight.
- Repeated failure category changes must update attributes without log spam.
- Security failures during optional enrichment must not be silently suppressed.
- Recovery callbacks must stop on unload and serialize with renewal operations.

## Task 1: Solus classification

Files: `solus.py`, transport/auth tests.
Interface: SolusError.retry_after: float | None, category: str, retryable: bool;
reference() retains finite safe stage/reason/status. Stages add loans, catalogue,
renewal. TLS failures are security errors; timeouts distinct from transport;
429/5xx/408 recoverable; HTTP credential errors only on credential submission;
checksession rejection is a session/protocol problem, not proof of bad PIN.
